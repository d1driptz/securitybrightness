# Persistent authority with explicit operator unlock

Persistence is opt-in: `python -m core.desktop --store "path/to/private/authority.db"`. The parent directory must already exist on a private local disk. The default desktop remains session-only. Do not use shared/untrusted directories, network shares, symlinks or someone else's database. Invalid existing stores fail closed rather than being reset. Only one store owner may run at a time.

Each record represents one application's current scope bundle. It stores identity, credential hash, scopes, trust, grant version, creation/change timestamps, lifetime and an expiry placeholder. Raw credentials are not stored. Version 1 supports persistent bundles without timestamp expiry; unknown/time-limited/one-shot modes are rejected, not interpreted as unlimited authority.

All persisted grants start inactive on startup. New registrations, permission changes and rotation also create inactive versions. Activation is never written to disk. Inspect the Applications view and explicitly confirm Unlock selected grant to activate that exact version for this session. Changed versions must be reviewed again. Unlock is not approval of a consequential request and executes nothing. Lock all deactivates stored authority; confirmed Revoke works while inactive and commits before success.

Application credentials, admin tokens, caller fields and restarts cannot unlock. No HTTP unlock route exists. Prototype A trusts the local Windows operator environment; it does not prove strong human identity or protect against malicious same-user processes.

Valid credentials for inactive/unavailable authority return HTTP 503. Invalid credentials return 401. Persistent mode rejects admin-token-only /check with 403 rather than permitting a bypass; default session-only mode retains that legacy path. Administrative lifecycle operations remain available while grants are inactive.

Registered HTTP requests capture registry and activation identity. After review, final revalidation and audit persistence serialize with lifecycle changes under the registry lock. Revocation, rotation, scope/trust changes, locking or lock-and-reunlock invalidate old requests; Approve cannot resurrect them. Invalidated requests return 503 without an allow audit record. Returned decisions are not execution capabilities or retroactively revocable. Embedded trusted Python integrations must explicitly pass a registry.authorization_lease guard to check_action for the same current-registry guarantee.

The SQLite backend validates a versioned document, uses an exclusive owner and transaction commits, and requests EXTRA synchronization in DELETE journal mode. Changes commit before publication in memory or success responses. Failed writes deactivate authority in that registry instance. Unknown versions, corrupt/duplicate records and unsupported lifetimes fail closed. The document limit is 4 MiB. [SQLite settings](https://www.sqlite.org/pragma.html) document the underlying locking and synchronization behavior.

Storage relies on the private directory's existing OS access controls. New files request owner-only mode where supported; Windows inherits the directory ACL. There is no DACL configuration, encryption, DPAPI, same-user tamper resistance or rollback protection. Restoring an older valid store can undo revocation even though grants restart locked; backup/restore is not implemented. Protect directory and journal files. Do not silently delete damaged stores as recovery.

Registry and decision-audit persistence are separate transactions; lifecycle/unlock history is not comprehensively audited. Synchronization cannot guarantee every OS/device/power-loss scenario. B requires stronger isolated human authority and storage custody. Session-only, time-limited, one-shot and resource-specific future grant policies need explicit implementation and tests. The service remains synchronous; SDK timeouts remain unknown outcomes and never imply permission.
