# Supplied-content analysis contract v1

Implemented: `file_security.analyze_bytes`, an independent standard-library-only Python component, plus a fixed worker and a narrow desktop header-review workflow. This is not a port of all browser rules or malware protection. The HTTP service has no analysis route. The desktop reads only an explicitly operator-selected regular file for this workflow.

## Threat boundary and authority

An already-authorized caller supplies an immutable bytes snapshot. Content is untrusted data, never instructions or a path. The analyzer imports no authorization modules and accepts no registry, credential, administrative context or operator callback. It does not open paths, execute samples, use a model, contact a network, alter grants or modify/quarantine files. The caller is responsible for legitimate acquisition; this API grants no right to read anything.

This is dependency/authority separation, not OS isolation: Python components sharing a process can compromise each other. The worker adds availability handling, not privileged isolation. A result is forgeable local data, not signed evidence, an authorization decision or an enforcement capability. Never use `status == "complete"` as permission to execute or as a safety verdict.

## Input and result

`analyze_bytes(content)` accepts exact `bytes` only, rejecting subclasses and other types with TypeError before invoking their methods. Inputs over 1 MiB are rejected before hashing or decoding. Accepted-size inputs use strict UTF-8 decoding; invalid encoding and C0 controls other than tab/CR/LF produce rejected results with no findings. This does not establish that remaining input is an ordinary text file. No extension guessing, lossy replacement, normalization, archive expansion or recursive parsing occurs.

Results are frozen snapshots with a detached JSON-compatible `to_dict()` view:

- `schema_version`: 1; `analyzer_version`: text-headers/1.
- `status`: complete or rejected; `reason`: null or input_too_large, invalid_utf8, unsupported_control_character. Unexpected internal exceptions propagate; adapters must report analysis failure, never a clean result.
- `byte_count` and `artifact_sha256`: exact supplied byte length/digest, with no digest for oversized input. A digest is content correlation, not provenance, authenticity, secrecy or proof that a current file still has these bytes.
- Findings: stable rule ID/version, evidence kind literal_header_pattern, priority review, total occurrence count and at most five locations per rule. Offsets/lengths are zero-based original bytes; lines and Unicode-code-point columns are one-based, with CRLF/CR/LF line breaks. Tabs and BOM count as code points, not visual columns.
- Limitations always accompany results. No raw source, snippets, filenames, credentials, permission booleans or human decisions appear in the result. A digest can still disclose equality or aid guessing; do not send results externally or retain them by default.

Exactly three case-sensitive literal markers are searched: BEGIN PRIVATE KEY, BEGIN RSA PRIVATE KEY and BEGIN OPENSSH PRIVATE KEY, each inside the conventional five-dash delimiters. They identify possible private-key headers, not valid private keys. Example documentation can match. Lowercase, extra spaces, Unicode substitutions, other key formats, encrypted/obfuscated content and malware without those strings can be missed. Numeric confidence and threat severity would not be justified by these rules.

The implementation makes three bounded searches over at most 1 MiB and computes at most 15 locations. This is a work/input bound, not an enforced wall-clock deadline, process memory quota or safe parser sandbox. Source bytes remain in caller/runtime memory; redaction is not secure erasure. Hashing a bounded rejected encoding does not imply that it was analyzed successfully.

## Evidence and migration

### Operator-selected desktop review

The File Security prototype tab offers private-key-header review, explicitly describing its three supported patterns. Selecting a file is a one-time operator request to read/analyze that file, not an application grant or a general file-execution capability. Nothing is scanned on startup or watched afterward. No content, path or analysis result is persisted to the decision audit or sent to a server. The UI shows an escaped, bounded filename, snapshot digest, redacted rule locations/counts and limitations; it does not show secret bodies or claim that dismissal/remediation occurred.

`acquisition.read_selected_file` accepts an absolute path, rejects existing symlink/reparse components and non-regular files, bounds reads to 1 MiB plus one overflow byte, compares the opened identity and checks size/mtime before/after copying. Windows UNC/device/alternate-stream paths are rejected. Mapped drives and filesystem providers are not independently authenticated: selecting such a path can cause ordinary OS filesystem/network access. No directory traversal, scanning of other files, writes or sample execution occurs. The caller must be the trusted operator workflow; this is not exposed as an application endpoint.

The panel runs one background job at a time. It now calls `worker.acquire_in_worker` to read the selected file in a fixed helper, then supplies immutable bytes to the separate fixed analyzer worker. The panel receives no registry, approval channel or authority callback. Incoming human-review requests still select the review tab and require the existing explicit response. Closing cancels UI timers and both helpers, fails outstanding authorization reviews as before and does not wait for file I/O on the UI thread; late reports do not touch destroyed widgets.

Important limits: acquisition is trusted helper code with normal account access. Its parent enforces a processing deadline and attempts kill/reap on timeout; this is not a hard real-time guarantee against OS process-creation delays, unkillable kernel operations or OS compromise. Path checks and size/mtime comparisons are not atomic confinement or a defense against hostile same-user replacement, concurrent edits with restored metadata, or kernel/filesystem compromise. Bytes are a snapshot, not a durable promise about a path. Source data can remain in runtime memory; no secure erasure is claimed. There is no strong sandbox, quarantine or broad File Security protection claim. Direct trusted callers of `read_selected_file` still perform synchronous in-process I/O without this wrapper's deadline.

Closure sets a cancellation event checked before child creation and during transport. Active acquisition or analysis is killed/reaped; acquisition completion cannot launch analysis after cancellation. After the UI loop ends, authority is locked and the review channel closed before waiting up to two seconds for job cleanup. Abrupt parent termination is not descendant containment and requires stronger OS process-lifecycle controls before any such guarantee.

`core/test_file_review.py` covers size boundaries, rejected paths/nonfiles, changed/error reads, real Tk-to-worker review, secret non-display, cancellation/failure, pending-review priority and closure during blocked acquisition. These are functional widget tests, not a manual visual/accessibility audit.

### Optional worker availability boundary

`worker.acquire_in_worker(path, timeout=5.0, cancel=None)` is the operator-selection adapter. Syntax validation performs no filesystem access in the parent. An ASCII JSON path string, bounded to 256 KiB, goes through stdin to the fixed `acquisition_entry.py`; no selected path is included in process arguments. The helper performs the existing read-only regular-file checks and returns raw snapshot bytes through a pipe bounded to 1 MiB plus one overflow byte. Fixed exit codes map to non-sensitive acquisition errors. Nonzero exit never produces usable content. Source bytes are intentionally returned to the trusted parent for digest binding and subsequent analysis; they are never rendered as matched snippets.

Both helper roles use one shared admission slot, isolated-mode Python, stripped environment, closed inherited handles, nonblocking transport, deadline/cancellation checks and exceptional cleanup rules. Only the two packaged entry points are allowed. The desktop uses separate five-second budgets for acquisition and analysis, so a review is not promised a single five-second total. There are no automatic retries. Acquisition remains a specifically operator-requested read, not a new HTTP capability or a general command/execution API. The helper is trusted to return the selected file's bytes; a digest cannot prove that provenance if its code/runtime is compromised.

`file_security.worker.analyze_in_worker(content, timeout=5.0)` now runs the same analyzer in a fresh, fixed Python child. It accepts only bytes and a finite timeout greater than zero and at most 60 seconds. Oversized input is rejected before starting a child. One request per parent process is admitted at a time; there is no unbounded queue or automatic retry. It remains synchronous, so a future GUI adapter must invoke it outside the human-review/UI thread.

The child receives samples only through stdin. The executable is the current Python runtime and the script is the packaged worker entry point: callers cannot choose a command, executable, path, environment or callback. Python runs with `-I -S`; the worker explicitly imports only from its installed project root and standard library locations. Child environment is limited to SystemRoot/WINDIR where present, inherited extra handles are closed, stderr is discarded, and Windows uses CREATE_NO_WINDOW. No sample is placed in command arguments, temporary files or logs. This launches the fixed analyzer, not an action executor or sample runner.

Nonblocking pipes bound input to 1 MiB and retained output to 16 KiB plus one overflow-detection byte. The parent checks a monotonic deadline, kills/reaps its child on failure, closes its pipes and releases its admission slot. All worker JSON passes the consumer validator against a parent-computed digest/length. Busy, timeout, output overflow, crash, transport failure, invalid output and cleanup failure raise AnalysisUnavailable with fixed non-sensitive reason codes, never an empty success result. The default deadline includes normal startup/transport/analysis time, but OS process creation cannot be preempted by this loop and cleanup may take up to an additional second.

This is availability containment of the fixed trusted worker, **not** a hostile-process sandbox, memory quota, restricted Windows token, job-object descendant containment or B. The child still has the same OS account privileges and can access resources if its code/runtime is compromised; environment stripping is not credential isolation from hostile same-user processes. The packaged code, Python runtime and installation directory must remain trusted under A. No core credentials or authority objects are intentionally handed to it. Windows nonblocking pipe support requires a supporting Python runtime (3.12+); unsupported transports fail explicitly without falling back to in-process analysis. The current environment tests use Windows Python 3.14.

If cleanup/reaping cannot be confirmed, admission stays closed until the parent restarts; repeated requests cannot accumulate potentially live children. The failure is explicit. Routine successful cleanup releases the slot. This exceptional restart requirement is not authority activation: persisted grants still restore inactive under the established operator-unlock rule.

`core/test_analysis_worker.py` exercises real child round trips, 1 MiB input, timeout kill/reap, output flooding, process failure, malformed/wrong-artifact responses, busy admission, launch failure and environment/launch configuration. No manual UI test, hostile-worker sandbox claim or malware detection evaluation follows from these tests.

Consumer validation is now available as `file_security.result_validation.validate_result(payload, expected_byte_count=..., expected_sha256=...)`. It accepts exact bytes containing at most 16 KiB of strict JSON. Expected metadata must be calculated/retained by the caller from its submitted snapshot, not copied from the response. Wrong metadata types are programming errors; invalid responses raise InvalidAnalysisResult without echoing source or parser messages.

Validation rejects duplicate/unknown fields, unsupported versions, non-finite numbers, boolean integers, mismatched content metadata, inconsistent complete/rejected states, unknown/repeated/out-of-order rules, unbounded counts/locations, invalid byte ranges and source/snippet fields. It reconstructs frozen results from only the allowlisted schema and requires the declared limitations. Unknown future versions fail closed until a deliberate migration. No wire result may supply an authorization field. `core/test_analysis_results.py` exercises these adversarial cases and valid round trips.

This validates structure and correlation, not completeness or truth. A malicious analyzer can omit findings or fabricate structurally plausible locations for a known digest. Locations are bounded but not checked against source bytes by this validator. The caller must trust the configured analyzer implementation within its declared threat model; no signature, process isolation, attestation or independent analysis is supplied. Parser depth failures, oversized messages and unexpected schema never become a clean result.

`core/test_file_security.py` covers original multibyte/line-ending locations, digest binding, positive/negative/evasion fixtures, bounded retained evidence, source non-disclosure, exact size boundary, malformed content, hostile input types, detached immutable output and internal faults. Synthetic fixtures establish narrow behavior; no detection benchmark, malware coverage or independent assessment is claimed.

Next dependencies: broader evaluated corpora and user-facing evidence/history. Acquisition now has the fixed helper's availability handling; stronger OS custody/lifecycle guarantees remain distinct future work. The desktop uses consumer-validated analyzer output without granting results authority. Retain the independent browser prototype until a deliberate migration has evidence and compatibility handling. Binary/archive parsers, remediation, external models and privileged observation are not implied by this contract.
